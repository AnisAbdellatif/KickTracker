# Decisions

Decision log (see AGENTS.md §3), tracked in git and public with the repo.

## Scope

**Current:** Track a chosen set of Kick channels (a handful at first, able to grow to hundreds or low thousands); Kick only, no other platforms. (updated 2026-09-24 04:04)

Tracking every channel on Kick is not the goal. Multi-platform (e.g. YouTube, as Streams Charts does) was considered and left out for now: adding `(platform, platform_id)` would cost little, but Kick-only keeps the model simpler, and our own channel ids leave the door open.

## Authorization

**Current:** One Kick app with an app access token (client credentials) for all public reads and webhook subscriptions; no channel owner authorization. (updated 2026-09-24 04:04)

Kick's docs: app tokens can subscribe to any channel's events by passing `broadcaster_user_id`. User tokens (owner logs in) are only needed for private data or acting on someone's behalf; kept for a possible later "streamer accounts" feature.

## Data Sources

**Current:** Official public API for polling (viewers, channel state), official webhooks for events, Kick's private v2 API only for the follower total, Pusher websocket for chat and raids/hosts. (updated 2026-09-24 04:04)

- The public API has no follower count; `channel.followed` gives gross follows only (no totals, no unfollows). v2 `followers_count` answered a plain `curl` from home (200, with the expected count for a test channel); must still be tested from the VPS. Read only that field, never store the rest (it has a signed `playback_url`).
- Chat stays on Pusher, not the `chat.message.sent` webhook: one HTTP request per message is heavy, and unverified apps are capped at 1 000 channels. The webhook is the fallback if Pusher stops.
- Webhooks have no raid/host event, so those stay on Pusher.
- v2 and Pusher are unofficial; both are isolated and optional so the rest keeps working without them.

## Tracking Cadence

**Current:** Viewers every 60s by polling `/livestreams` for **every** tracked channel (not only the live ones); stream start/end and title/category from webhooks, with the 60s poll as the safety net; subscriber counts and slug renames from `/channels` every 5 minutes; followers every 15 min live, daily offline, plus at stream start and end; chat per minute. (updated 2026-09-24 12:40)

Owner's spec for the cadences. Kick refreshes `viewer_count` about every 60s, so the owner moved viewer polling from 15s to 60s. Hours watched caps Δt at 75s: a cap equal to the interval would undercount every slightly late poll, while 75s fills at most 15s of a missed poll. The plan polled `/livestreams` only for channels believed live and relied on the 5-minute `/channels` poll to notice a missed start; polling every tracked channel costs one request per 50 channels a minute and notices a missed start within a minute, with one code path for stream state instead of two. `/channels` keeps the jobs only it can do (subscriber totals, renames).

## Stream Identity

**Current:** A stream is keyed on `(channel_id, started_at)` using Kick's `started_at`. The pure `Metrics.Sessionizer` turns status events and poll readings into streams: Kick's end event always wins and a stream it closed never reopens; without it a stream ends at its latest live evidence, which only ever moves later; a newer `started_at` closes the previous stream; a poll must miss the channel for 90s after the last evidence before it counts as offline; a poll-closed stream seen live again after the offline poll reopens (Kick keeps `started_at` through short disconnects); evidence about an unknown older stream records it. The same rules are enforced in the upsert SQL for streams no longer in memory. (updated 2026-09-24 12:40)

Kick sends no livestream id in `livestream.status.updated` or `GET /livestreams`. Both report `started_at`, so it is the only key both paths agree on (confirmed on recordings). The rules were chosen so arrival order doesn't change the result; property tests shuffle and repeat a true history's observations (start and end events, readings every minute, the API's ~20s lag after an end, offline polls) and check the outcome. They found one order dependence: offline polls arriving before any evidence of the stream they follow were ignored. Fixed by keeping the latest offline poll even when no stream is open. The 90s grace is there because the API lags Kick's state (a start event can precede the stream appearing in the API). Mutations of the rules were checked to fail the properties.

## Backend Language

**Current:** Elixir / Phoenix. (updated 2026-09-24 04:04)

Compared with Go and Bun. At our scale all three handle the load; the deciding factor is staying correct for months: supervised process per channel, crash isolation, fair scheduling, cheap websockets, LiveView + PubSub for live pages, Oban, Broadway, built-in clustering. Go needs hand-written supervision and a separate frontend; Bun (briefly chosen before) shares one event loop, so one bad channel can stall or crash all, and Next.js needs a relay for live data. Cost: learning OTP.

## Architecture

**Current:** Three parts: ingress (webhook receivers) → RabbitMQ → app. The app runs as two roles, `collector` and `web`, from one image, deployed separately. (updated 2026-09-24 04:04)

Owner requirement: updating logic must never stop webhook intake. The app only knows the queue, so who receives webhooks and how redundantly is a deployment choice (self-hosted receivers now, Cloudflare/managed later). A separate BEAM process tree alone adds nothing (Phoenix already isolates requests); hot code upgrades were rejected as routine deploys (complex, poor fit with containers) but kept as an occasional tool.


## Collector Availability

**Current:** Two collectors run; one leads and collects, the other stands by (`Collector.Leader`, rules in the pure `Collector.Lease`). The lease is a Postgres advisory lock on the Leader's own connection plus a `collector_lease` row whose epoch rises at every change of holder; `collector_terms` records each term and why it ended. A standby (checking every second, on the database's clock) takes over at once when the leader released the lease on a clean stop, or when the lock is free and the database did not restart since the leader's last heartbeat (its session ended: a crash); it ends the session of a leader that holds the lock but has been silent for 6s (frozen or cut off) and then takes over; after a database restart it gives the leader 10s to take its lock back. A node restarting takes its own lease back at once; the leader heartbeats every second. The leader keeps collecting while the database is unreachable and stops at once when superseded or when another node holds the lock. Every collected write goes to a local SQLite journal (`Collector.Journal`) as a data operation naming streams by `(channel, started_at)`, and a Writer applies it to Postgres exactly once (a high-water mark per journal in the same transaction), waits out the database with backoff, sets aside writes that can never apply, and drops writes an older holder made after a newer one started (fencing by epoch). Polled data comes from `Collector.Source` modules run by one `SourceRunner` (cadence, concurrency, deadlines, isolation, coverage, journaling); chat stays one socket per channel, journaling through the same path. A watchdog restarts collection if the viewers source stops completing cycles; the collection tree is restarted with backoff and can't take the node down. Each collector has a loopback status endpoint (container healthcheck, deploy script) and a `collector_nodes` heartbeat row read by web. (updated 2026-09-24 19:30)

The owner's requirement: the web role can restart freely, collection must not stop. The audit that led here found the collector crash-looping the whole node when the database was away (the Manager and Poller raised on every restart, beyond the root supervisor's default 3 restarts in 5s), nothing buffered, deploys a stop-then-start gap, a poison event able to stop a channel for good, a chat upgrade able to hang forever, polling batches run one after another with uncapped `retry-after`, and nothing outside the collector noticing it dead.

Alternatives: **one collector with faster restarts** fixes crashes but not deploys or host-level restarts, and every restart is still a gap. **Two collectors active at once** (both polling, both chatting) would need every write idempotent across nodes; chat counts are additive by nature (late messages add to a written minute), so double collection would double them. **Leader election through Oban's peer or Erlang distribution (`:global`)** would tie the lease to clustering, which the roles don't otherwise need, and `:global` splits on a partition; a lock in the one database every node already shares has no split-brain, and the epoch fences the one race it has (a database restart freeing the lock while the old holder still runs). **Buffering only on failure** (write directly, spool when the database errors) would leave two write paths, one of them rarely exercised; journaling everything means the tested path is the path. **Memory-only buffering** loses what was waiting if the collector restarts during a database outage; the owner chose the disk journal. **Chat as a polled source** doesn't fit (it's a socket per channel), so the behaviour covers polled sources and chat shares the journal, coverage and status plumbing.

Takeover timing: the first version waited 15s of silence plus 5s of a free lock before taking over from a crashed leader, to let a leader whose connection blipped get its lease back; a free lock with the database not restarted since the leader's last heartbeat (`pg_postmaster_start_time()`) already means the leader's session ended, so that wait now applies only after a database restart, and a crash is taken over within a second. The same review found a hole: a leader frozen or cut off with a half-open connection keeps its session, and the lock, until TCP notices (hours by default); the standby now ends that session (`pg_terminate_backend`, allowed between sessions of the same database user) after 6s of silence. A false positive (a leader briefly too slow to heartbeat) costs a handoff, fenced, not data. Every query on `pg_locks` is scoped to the current database: advisory locks are per database but the view is server-wide, and an unscoped check let a shadow on the same server end the primary leader's session. A leader process starting stops any collection tree left in its slot by an earlier incarnation (one that crashed without stopping it), and its default hooks are plain calls rather than stored functions, which a code reload would invalidate. For the machine itself going, see Shadow Collector. A channel process that starts during a database outage without a snapshot starts afresh, so a stream that ended meanwhile may be closed later by its end event rather than by polling.

## Channel Isolation

**Current:** Each channel's `ChannelSup` is `:temporary` under the shared `Tracking.ChannelsSupervisor`: a channel whose processes keep crashing gives up on its own (10 restarts in 60s) and the `Tracking.Manager`, which monitors every one, quarantines it: logged as an error, listed in the collector's status, and started again after 1 minute, doubling with each failure in a row up to an hour (10 minutes of running starts the count over). Children start from the channel's row as `Collector.Tracked` knows it at that moment, and row changes travel as the changed fields only (`{:channel_fields, fields}`, `Tracked.update/2`, serialized), never as a whole row. Events handed to a `ChannelServer` at start are counted in the journal; one that took the process down at 3 starts in a row is marked processed and logged, and stays in `webhook_events` for a replay. (updated 2026-09-24 21:45)

With `:permanent` channel supervisors, a channel crash-looping (a poison event replayed at every start) spent the restarts of the supervisor all channels share and took every channel down, then the collection tree. Letting the channel's supervisor give up alone and restarting it from the Manager with a backoff keeps one bad channel's trouble its own and still retries it without anyone acting. Alternatives: a larger shared budget only delays the cascade; a per-channel `DynamicSupervisor` adds a process per channel for what a monitor in the Manager does. The frozen row: the child spec carried the channel as it was when the channel started, so a restart brought back a row without the chatroom id learnt since, and the chat socket never connected again; whole-row broadcasts from processes holding older copies could also undo a field another had learnt. Quarantine state lives in the Manager's memory: a restart of the collection tree starts it over, which is acceptable since the channel's own supervisor limit applies again.

## Shadow Collector

**Current:** An independent collector on a second machine with its own database (`COLLECTOR_MODE=shadow`, `compose.shadow.yml`), collecting the same channels all the time (polls, followers, chat; no webhooks, no subscriptions, no site). It copies the channel list and removal requests from the primary's database every minute over the private network with a read-only user, keeps its last list when it can't, and notifies after 5 minutes of not reaching the primary. The primary side's `Workers.Backfill` reads the shadow's database every 5 minutes and, per channel and source over the last 7 days, copies the shadow's rows for the ranges the shadow covered and it didn't, as `Collector.Ops` (ours always win; chat only for whole minutes we have nothing for), recording each filled range in `coverage` with `collector = 'shadow'`. Its own Kick app, its own heartbeat; alerted on when unseen for 15 minutes. Keeps 30 days, not backed up. (updated 2026-09-24 19:30)

The owner wants collection to survive the main VPS going, and asked for a collector that could run elsewhere. A standby on another machine can't: the lease, the journal's destination and everything it writes are in the main VPS's database, which goes with the machine; making it work would mean a replicated database with failover (stage 3), a much larger change. Collecting all the time into a database of its own needs none of that, has no takeover at all (it was already collecting), and covers every cause of a gap on the primary side, not just a machine failure: a bug, a bad deploy, both collectors down. Its data joins ours the way an import does (natural keys, existing rows win), so the machinery was already there. Alternatives considered: the shadow writing into the primary's database when it's back (it would need to know when the primary missed something; the primary knows its own coverage, so it pulls); streaming the shadow's journal to the primary (couples the two formats, and the shadow's data is useful on its own); webhooks on the shadow too (the backup receiver already spools them, and two consumers of Kick's subscriptions would fight). The cost is double polling and chat connections, which Kick sees; a second Kick app keeps the shadow's token and limits independent. Chat minutes the primary had partly (the minute an outage began) keep the primary's partial count rather than risk counting twice.
## Queue

**Current:** RabbitMQ: topic exchange `kick.events`, quorum queue `kick_tracker.events`, publisher confirms, dead-lettering, consumed with Broadway (`broadway_rabbitmq`). (updated 2026-09-24 04:04)

Owner's choice over NATS JetStream. RabbitMQ has the official Broadway producer and runs on the BEAM; managed option (CloudAMQP) needs no app change. NATS was lighter with built-in dedup, but its Elixir support is community-only. No built-in dedup in RabbitMQ is fine: the app dedupes on `message_id`.

## Ingress and Redundancy

**Current:** Minimal Elixir receiver (verify, envelope, publish with confirms or spool to local SQLite, answer 200), never touching the database. Stage 1: two receivers on one VPS behind Caddy; stage 2: backup receiver on a second VPS routed by Cloudflare Load Balancing, publishing to the main RabbitMQ over the private tunnel (5672 published on `PRIVATE_IP` only, plain AMQP inside WireGuard/Tailscale), with HTTPS from a Cloudflare Origin CA certificate; stage 3: redundant queue if ever needed. (updated 2026-09-24 21:50)

Missed webhooks are lost forever. Kick unsubscribes after failing "for over a day"; its retry policy is otherwise undocumented (to test). A backup on another machine can't depend on the main database, hence the local spool. DNS round-robin rejected (client-dependent failover); floating IP rejected as primary option (same provider only). The backup machine can't get a public certificate itself: Cloudflare routes the host to the main VPS, so HTTP-01 and TLS-ALPN challenges never reach it; DNS-01 would need a Caddy build with the Cloudflare DNS plugin and an API token on that machine, while an Origin CA certificate is a file, trusted only by Cloudflare, which is the only client there. AMQP over TLS was considered for the link and left out: the tunnel already encrypts it, and publishing only on the private address keeps it off the public internet.

## Event Envelope

**Current:** Receivers wrap each delivery in a JSON envelope (`contracts/envelope.md`, version 1) carrying the raw body and signature; the app re-verifies. Fields named `event_type` / `event_version` for Kick's values and `envelope_version` for ours; `message_id`, `sent_at` and `body` copied byte for byte; non-UTF-8 bodies travel as `body_base64`. Contract: at-least-once, no ordering, ack after commit, short queue retention with `webhook_events` as the permanent record. (updated 2026-09-24 04:20)

Keeps the app independent of the ingress and trusting neither the queue nor the receivers. The first sketch had a single `version` field, which would have mixed up Kick's payload version with our envelope's version; they change for different reasons, so they are separate. `sent_at` is kept verbatim (not parsed) because it is part of the signed text. Changes are backward-compatible only; consumers ignore unknown fields.

## Database

**Current:** PostgreSQL + TimescaleDB, one database, self-hosted. (updated 2026-09-24 04:04)

Compared with plain Postgres (portable, no compression, own rollups) and Postgres + ClickHouse (best analytics, two databases, no transactions/unique keys on the ClickHouse side). With the chat structure below every heavy query is small at our scale. Cost: compression and continuous aggregates aren't offered by generic managed Postgres, so self-host or Timescale's cloud. Growth path: ClickHouse alongside Postgres (Plausible's model).

## Data Model

**Current:** Store append-only raw facts, derive everything else; own channel ids with `kick_user_id` unique; slugs with history; UTC storage with the channel's timezone applied at read time; title/category as a change log with derived segments, and category also on each viewer sample. Daily and weekday figures are built from UTC hours: a stream crossing midnight counts in both days, hour by hour; for a timezone that isn't a whole number of hours from UTC they are approximate to the hour, and the API says so in a `note`. Category URL slugs keep letters and digits of any script (accents dropped from Latin letters only), fall back to a short hash of the name, and a slug taken by an earlier category gets the id appended; lookup ignores case. (updated 2026-09-24 21:50)

Lets any formula change later and history be recomputed. Slugs change on rename. Weekday/daily figures in UTC would be wrong for the channel's audience. Counting a midnight-crossing stream for the day it started, as first written, would need per-stream daily rollups; splitting by hour is what `hourly_stats` gives and keeps daily sums equal to hourly ones. A 15-minute rollup (or raw samples at read time) would make half-hour zones exact, at four times the rollup's size or a slow heatmap, for few channels; a note was chosen until one needs it.

## Chat Storage

**Current:** Three levels: `chat_minutes` (counts per channel-minute, forever), `chat_minute_users` (per chatter per minute, 90 days by retention policy), `chat_stream_users` (per chatter per stream, forever). No message text ever. The `ChannelServer` gathers chat per minute of Kick's own timestamp (pure `Metrics.ChatMinutes`, deduplicated by message id) and writes a minute 30s after it ends, every 15s, and everything on shutdown. A message arriving after its minute was written is added to it: `chat_minute_users` rows add up, and `chat_minutes` is recounted from them. A minute belongs to the stream live during it; offline chat is counted with no stream. When a stream becomes the open one, the channel's minutes already written with no stream inside it (from its start to now) are given to it and their chatters added to `chat_stream_users` from `chat_minute_users` (a journaled `{:chat_stream, ...}` write, idempotent: only minutes still without a stream move). (updated 2026-09-24 21:45)

Unique counts don't add up, so arbitrary windows need per-user rows. Windows inside a stream read only that stream's rows; long-range questions use the per-stream table, 20–50× smaller. 90 days (owner's choice) caps the largest table and limits personal data. HyperLogLog / roaring bitmaps kept in reserve. Recounting `chat_minutes` from the per-user rows, rather than adding counts, keeps "distinct chatters in the minute" right when a late message's sender was already counted.

Attribution when a stream's start is learnt late (a missed start event, the API's lag): minutes flushed before the stream was known were written with no stream and, `chat_minutes.stream_id` keeping its first value, stayed outside the stream for good, missing from `chat_stream_users` and so from every per-stream chatter figure, unrecoverable once the per-minute rows expire after 90 days. Two ways were considered: attributing by time at read time (as follows and support events are), or giving those minutes to the stream when it opens. Read-time attribution would mean rebuilding `chat_stream_users` from `chat_minute_users` by stream range, which stops being possible after 90 days, and the per-stream table is exactly what outlives them. `chat_minutes.stream_id` and `chat_stream_users` are derived from the per-minute rows and the streams' ranges (the minute row is already recounted on every write), so setting a still-empty link is completing derived data, not changing a raw fact. First and last times added this way have minute precision.

## Chat Socket

**Current:** One `ChatSocket` per channel (Mint.WebSocket in a GenServer, under the channel's `rest_for_one` supervisor, after its `ChannelServer`). It subscribes to `chatrooms.<chatroom id>.v2` and, once known, `channel.<kick channel id>` (learnt from `/livestreams`' `channel_id`); answers pings, pings after Pusher's activity timeout and reconnects if no pong comes in 30s; drops an upgrade that doesn't complete in 15s, closing the connection on every error path; decodes frames that arrive in the same read as the 101 upgrade. Reconnects with backoff 1s→30s with jitter (between three quarters of the backoff and all of it); the backoff resets only after a connection has stayed subscribed for a minute. It starts from the channel's row as it is when it (re)starts and follows field changes (an id learnt; a chatroom id that changes moves it to the new chatroom). Chat coverage is extended every minute while subscribed and closed on disconnect. It waits until the chatroom id is known. (updated 2026-09-24 21:45)

Our own GenServer over Mint rather than WebSockex: the process owns the connection and the reconnect and coverage logic, as planned in §9. Resetting the backoff on every successful subscription turned a server that accepts and then drops at once into a reconnect every second or two; requiring a minute of stability keeps quick recovery after a real outage without that loop, and jitter keeps sockets dropped together (a Pusher restart) from all reconnecting in the same instant.

## Raids and Hosts

**Current:** Not parsed yet. Their Pusher event names were never recorded, so nothing guesses them: every chat-feed event the parser doesn't know is reported to the `ChannelServer` by name only (its data is dropped) and logged once per name per channel. `channel_events` exists (with a `dedup_key` unique per channel, and `other_channel` as text) for when a recording shows the names and fields. (updated 2026-09-24 13:40)

AGENTS.md forbids writing payload shapes from memory or documentation. Logging unknown names means the first real raid seen in production (or a recording) says what to parse, without having stored anything it carried.

## Frontend

**Current:** Phoenix LiveView for public site and admin; history served as cacheable JSON (`/data/v1`), only live data over LiveView; server-side resolution by range (≤ ~2 000 points, avg + max per bucket); English first, Gettext and RTL-ready layout. Visual style: daisyUI with our own light and dark themes (warm neutral canvas, white cards, one blue accent, flat with 1px borders), a sticky header, segmented controls for period and metric, underline tabs, and channel initials on a palette tint instead of avatar images. (updated 2026-09-24 15:00)

Keeps per-visitor memory tiny (no chart data in assigns) and lets Caddy/Cloudflare cache history. Max per bucket prevents downsampling from hiding peaks. The themes replace daisyUI's defaults, whose orange/indigo clashed with the chart palette; status colours (success/warning/error) are kept apart from the categorical hues. Initials rather than Kick's avatar images: nothing to fetch, store or hotlink, and they stay stable when a channel changes its picture.

## Charts

**Current:** Apache ECharts 6, installed from npm into `app/assets` (package.json), imported modularly (only line, bar, pie and heatmap and the components used) and loaded by dynamic `import()` from the one `Chart` hook, so esbuild splits it into its own chunk (esbuild now runs with `--splitting --format=esm`, and `app.js` is a module script). Chart kinds: `timeseries`, `stream`, `bars`, `share`, `heatmap`, `sparkline`; the server sends data, a kind and labels/columns, never options. Table view and CSV export in the hook, from the same JSON. Colours are CSS custom properties (`--viz-1..8`, `--viz-seq`, chrome tokens) read by `charts/theme.js`: an eight-hue categorical palette in fixed order with separate light and dark steps, one blue ramp for heatmaps, 2px lines with a ~10% area wash, hairline grids, bars capped at 24px with rounded data ends, a legend only for two or more series. Time charts open zoomed to the stretch that has data (the hook computes it from the series, 2% room either side) on an axis spanning the whole period; the reader's zoom survives re-renders (live points, theme), and double-click or a "show all" button fits the data again. Charts whose range ends now fetch their data again every 60s (`data-refresh`, set by the page: preset periods and live streams), paused while the page is hidden; the home sparklines are fetched from `/data/v1/sparklines/:slug?at=<minute>`, the minute moved by each live broadcast. Streamer-controlled text in tooltips is HTML-escaped (`escapeHtml` in `charts/theme.js`); the stream chart's crosshair tooltip lists the title changes, markers and category near the hovered minute, since the ticks themselves are too small to point at. Text the charts show (units, "Other", marker kinds, the error overlay) comes from the page through Gettext; weekday names come from the browser's `Intl`. (updated 2026-09-24 23:30)

Needs shaded bands (category segments, no-data), event markers (raids, gifts), linked zoom across panels, heatmaps and dense series in one library. Chart.js (earlier pick) needs plugins for most of that; uPlot is faster but too narrow. The full ECharts bundle was 2.8 MB unminified; modular imports bring the chart chunk to about 670 KB minified, loaded only on pages with charts. `stream` was added to the planned kinds: the stream page's three stacked panels sharing one zoom are one ECharts instance, which a generic `timeseries` couldn't express without sending options. The palette replaced Okabe–Ito because Okabe–Ito's yellow and sky blue fall below contrast on a light surface and it has no matched dark steps; the new one was run through a colour-vision-deficiency check (adjacent pairs, both themes) and passes, with the light-mode contrast warning covered by legends and the table view. Tokens live in CSS so the charts, avatars and meters share them and a theme switch re-renders charts from the same source. Fitting by default instead of cutting the axis to the data: the empty part of a period is real information (we weren't tracking yet, or weren't collecting), so it stays one zoom-out away rather than hidden. The zoom is applied as the dataZoom window by the hook, generically for every time kind, so kinds stay unaware of it; before, each re-render replaced the chart's state and reset any zoom, every minute on a live stream page.

Charts used to be fetched once, when the page loaded: only the stream page's viewer line grew (by `push_event`), so a channel page, the compare page or the home sparklines left open stopped at the moment they were opened. Sparklines used to be rendered into the page as `data-values` from LiveView assigns and never moved (their element is `phx-update="ignore"`); a small per-channel endpoint keeps chart data out of assigns like every other chart, and the minute in its URL is what makes the ignored element refetch. Refetching the same cacheable URL was preferred over pushing every series' new points through LiveView: it covers every kind (heatmap, shares, chat, events) with no per-kind append logic, keeps chart data out of LiveView as the design requires, and costs one small, cached request per chart per minute.

## Public Site Data

**Current:** Charts read `/data/v1` JSON (columns: `t` in unix seconds plus one array per value; `gaps` from coverage), with an ETag and `Cache-Control` of a day for ranges ended more than two days ago and 30s otherwise. The resolution is picked by the pure `Series.Resolution` so no series has more than 2 000 points: raw ≤ 12h, 5 min ≤ 6d, 15 min ≤ 20d, hourly ≤ 80d, 6-hourly ≤ 200d, daily below 2 000 days, weekly beyond (days and weeks in the channel's timezone); custom ranges are capped at 20 years; follower totals use the same buckets (last, min, max; empty buckets left out). `res` may only ask for fewer points. Hourly and longer series read `hourly_stats`; 5- and 15-minute viewer buckets leave out excluded streams and flagged readings' max, as the rollup does. Chat counts are 0 only where chat coverage says we were listening, subs/gifts/Kicks only where ingress coverage does; empty viewer buckets are null. Active chatters are null where the window reaches before the 90 days of per-minute detail. The JSON API serves only public channels (stream chatters included), and support only while `support_page_public` is on. Expensive aggregates go through `KickTracker.Cache` (ETS, TTL 60s for periods reaching into the last two days, an hour otherwise); a preset period ends at now rounded up to the next minute so its cache key repeats. "all" without a channel starts at the earliest public channel's `tracked_since`. Follower gain falls back to the first reading in the period when none precedes it, labeled with its time. New vs returning chatters per stream is computed by the rollup into `stream_stats.new_chatters`. (updated 2026-09-24 21:50)

Cachex was planned for the query cache; a 60-line ETS table with a TTL and a sweep covers what we need without a new dependency. Computing new chatters at read time took 2.7 s for a big channel's month (it had to find every chatter's first stream) and timed out a test; per stream in the rollup it is about 0.2 s once. The resolution ladder was redrawn when 7d at 5 minutes (2 016), 90d hourly (2 160), 90 days of raw follower readings (8 640) and 20 years of days (7 300) all passed 2 000 points; 15-minute and 6-hour buckets keep the presets close to their old density, and weeks cover any long range. Rounding a preset's end up to the minute (rather than down, or to the bucket) keeps the latest reading inside `[from, to)` and moves at the pace charts refresh. Active chatters read `chat_minute_users` with bounds on its own `minute` column (each chatter-minute expanded to the window it counts in): the earlier join against a generated series of minutes read the channel's whole history once per minute and timed out. Pages reproduce from their URL: `period=24h|7d|30d|90d|1y|all` or `from`/`to`.

## Stream Corrections

**Current:** `stream_overrides` (exclude, merge; revocable, never deleted) layered over the raw streams. `merged_streams` is a view of active merges, one level deep; `merge_groups` resolves them transitively (each merged stream with its root). A merge is recorded into the root of the earlier stream's group and allowed when every stream in between is already in that group, so a broadcast split in three becomes one stream however it is merged; merged streams disappear from lists and counts, the root runs to the last part's end, its `stream_stats` cover every part (airtime is the parts' sum; each part's first sample is weighted from its own start, as in `hourly_stats`), and a merged stream's page redirects to the root. `excluded_streams` is a view of active exclusions plus the streams merged into them, which every stream and viewer figure filters on (KPIs, hourly viewers, 5-minute series, records, categories, notable moments, chatter retention, overlap, "earlier stream" for new chatters); excluded streams stay listed, marked. Split is allowed by the table but not built. (updated 2026-09-24 21:50)

Raw facts are append-only (AGENTS.md §7), so a correction can only be a row on top. A view keeps the filter in one place for SQL, and resolving chains in a view (rather than rewriting older one-level rows) keeps merges made before the view existed correct. Split needs an address for each half (a stream is its row and id), which merging doesn't; it waits for a real case. Hourly rollups leave out an excluded stream's viewer samples, so channel totals and leaderboards agree with the stream list; follows, chat messages and support during it still count toward the channel's totals (they happened, and are counted by time, not by stream), while figures built from streams (chatters per stream, overlap, retention) leave it out. Changing an override rebuilds the rollups of every stream of the group and their hours.

## Admin

**Current:** Under `/admin` in the `web` role, invite-only, password + TOTP on every login; optionally only reachable over the private network. Accounts are written by hand on phx.gen.auth's model (random session tokens in the database, looked up per request and per LiveView mount; logout deletes the token and disconnects live pages), not generated: PBKDF2-HMAC-SHA512 from OTP's `:crypto` (210 000 iterations, count kept in the hash) instead of bcrypt, and our own RFC 6238 TOTP (`Admins.TOTP`, tested against the RFC's vectors) that refuses a code for a step already used. Invitations are one-use links valid 7 days, stored hashed, shown once to the inviting admin to send by hand, with the token in the query (`/admin/invite?token=…`; the old path form still opens and isn't logged); the first comes from `mix kick_tracker.admin.invite` / `KickTracker.Release.invite/1`. Accepting re-checks the invitation (still there, not expired) inside the transaction that uses it up. An open admin page is held to its session three ways: disabling an admin or changing a password deletes their session tokens and broadcasts `"disconnect"` to each token's live socket id; an `on_mount` hook re-checks the token (one indexed query) before every event and sends the page to the login if it's gone; and the page checks again at the token's expiry. Disabling an admin also deletes the invitations they created. Every admin action goes to `admin_audit_log`, ErrorTracker's resolve/mute/unresolve/unmute included (seen by the same hook, since ErrorTracker doesn't say who acted); LiveDashboard runs with `allow_destructive_actions: false`. Login and account forms take only strings: any other shape is a 400 (and a counted failure) or a form error, never a crash. Corrections are layered on raw data, never edits. (updated 2026-09-24 23:10)

phx.gen.auth in Phoenix 1.8 generates magic-link login by email and public registration, both of which would have to be torn out (no mail is configured, no public sign-up), and it adds `bcrypt_elixir`, a native dependency; TOTP would have needed `nimble_totp`. The pieces kept from it are the ones that matter for security (server-side session tokens, renewing the session on login, disconnecting sockets on logout, and on disable and password change too). The disconnect broadcast alone isn't enough: it only reaches sockets whose session has the id, and a page could outlive a token by age, so the per-event check stays as a second layer; caching it was not worth it, admin events being few. The invitation token moved out of the path because Phoenix logs request paths verbatim (query strings not, and params go through `filter_parameters`); exchanging the token for a session value on first visit would still log that first request. The enrolment shows the secret and the `otpauth://` URI as text rather than a QR code, to avoid a QR library; any authenticator app accepts a typed key. Login failures give one message for every factor, and an unknown email costs as much time as a wrong password.

Timezones are validated against PostgreSQL's `pg_timezone_names`, which is also what applies them at read time; the add form suggests one from the stream's language, always editable. ## Health Page

**Current:** The health page reads only the database (the collectors from their `collector_nodes` heartbeat rows and `collector_terms`, plus RabbitMQ's management API, when `RABBITMQ_MANAGEMENT_URL` is set, through a `monitor` user with the `monitoring` tag and empty permissions), so it works on a web node. A source's state comes from its latest `coverage` outcome: ok, failing, stale (older than a little over two cadences) or never. Coverage % is the pure `Metrics.Coverage.fraction/4`: each ok period vouches for its first to last outcome plus one cadence. `webhook_events` gained a nullable `broadcaster_user_id`, filled from the body when stored, for "last event per channel". (updated 2026-09-24 06:20)

The collector's processes know more (socket state), but asking them from a web node needs clustering, and the database already records every outcome. Without the column, the last event per channel would mean decoding every recent body, and `convert_from` fails on a non-UTF-8 body. Rows stored before the column stay null rather than being backfilled (raw rows aren't updated). The monitoring user needs a permission entry in the vhost (empty patterns) to see its queues through the API.

## Admin Operations

**Current:** Admin actions that change collected data run on the collector as Oban jobs the web node queues: `Workers.Reprocess` (recompute rollups for a range and given streams; replay stored `webhook_events` through the current handlers, skipping redacted ones) and `Workers.Privacy`. Dead letters are handled from the web node over AMQP as a dedicated `ops` user (read the dead-letter queue, write the exchange): listing takes messages unacknowledged and puts them all back, and waits (up to 2s) until the quorum queue shows them ready again before returning; a replay is acknowledged only after RabbitMQ confirms the republish (waiting up to 10 s: the AMQP library counts that timeout in seconds); a discard needs a reason, kept in the audit log with the message's id and type. A dead letter is named by a key, a hash of its message id and bytes, so one without an id can be acted on and copies of one message are listed once and replayed or discarded together; two different messages under one id must be named by key. Replay and discard search the whole queue (up to 20 000 messages), not just the first page. A dead letter naming a Kick id in `removals` is shown redacted and refused for replay (only discarded). Groups are admin tables with a public flag; settings are feature flags and the revenue assumptions, with defaults in code, so an empty table works; they are saved all or none in one transaction with one audit entry, each number checked against a range (share 0–1, prices up to 1 000 USD, a Kick up to 100 USD). (updated 2026-09-24 23:10)

Refusing the replay of a message naming a removed person, rather than scrubbing it on replay: the envelope's body is signed, so a scrubbed body would fail the consumer's signature check and come straight back; and the dead-letter user lives on the web node, while a deletion runs on the collector, which doesn't reach RabbitMQ as that user, so purging the queue at deletion time isn't available. Putting messages back in a quorum queue lands asynchronously: without the wait, a count, a listing or a replay right after a listing could miss them (a replay answered "not found"), which also made the dead-letter test fail about one run in three. The web role writes only admin tables (AGENTS.md §8), so anything touching raw or derived tables is a job, which also survives a web redeploy mid-action. Dead letters live in RabbitMQ, not the database, so the web node needs its own least-privilege broker user rather than borrowing the consumer's. Polling cadences were planned as settings; they stay in code because the 75s hours-watched cap and the coverage gaps are derived from them.

## Privacy Deletion

**Current:** A deletion request (admin, confirmed by retyping the Kick user id) removes the person's username and per-person chat rows, sets their id to null in `follows` (now nullable) and `support_events` so the counts stay, scrubs them from support payloads, and redacts `webhook_events` bodies that name them, marking those rows `redacted_at` (they no longer verify against Kick's signature and are never replayed). Aggregates already computed stay. The privacy page audits a search without the term (only whether it was by id or username and whether anyone was found); a migration forgot the terms already logged, and a deletion also clears the target of any `privacy.find` audit entry naming the person by id or username (left by an older version still running during a deploy). Dead letters naming a removed id can't be replayed (see Admin Operations). (updated 2026-09-24 23:10)

This is the one exception to append-only raw facts, because the law requires it; it is audited. The audit log is append-only too, with the same exception for personal data: a search term is often a username, sometimes of someone we hold nothing about, and was out of reach of a deletion; the search itself stays recorded. Nulling ids instead of deleting rows keeps follows, subs and gifts counted, which identify no one once the id is gone. The body search is by the id's digits, so it may look at bodies that only contain them inside a longer number; the JSON-aware scrub changes only real matches.

## Alerts and Errors

**Current:** Alerts are evaluated every minute by the pure `Alerts.Rules` over a snapshot (per channel: live, last poll, chat, 24h coverage; system: last webhook, oldest unprocessed event, dead letters, queue depth, clock drift; the collectors from their `collector_nodes` heartbeat rows: none collecting, a standby gone, writes waiting in a journal for over 5 minutes, writes set aside, the shadow collector unseen for 15 minutes). They run on the leading collector (`Workers.Alerts`) **and** on web nodes (`Alerts.Ticker`); a transaction-scoped advisory lock lets one check at a time. Each problem has a stable key and a row in `alerts` while it lasts: notified when it starts, reminded every 6 hours, and notified when resolved. Targets: a Discord/Slack webhook (`ALERT_WEBHOOK_URL`) and/or Telegram; `HEARTBEAT_URL` is pinged each minute by the collecting node as a dead man's switch. Errors go to ErrorTracker (in our database, dashboard at `/admin/errors`), including crashes of any process through a `:logger` handler, and a new kind of error is notified. Its stored context goes through `KickTracker.ErrorFilter` (ErrorTracker's `filter` option): values under keys naming a secret (password, code, token, secret, totp, …) at any depth, and invitation tokens in paths and query strings, become `[FILTERED]`; Phoenix's `filter_parameters` uses the same list for logs. `/healthz` is for external uptime checks. (updated 2026-09-24 23:10)

A job on the collector can't report the collector being down: checking from web too covers a dead or stuck collector while the site runs, and the heartbeat to an outside service covers both. Collector rules say nothing where no collector ever reported, so a site-only deployment stays quiet. Host-level checks (disk, certificates, backups) are scripts in `deploy/`, not the app. ErrorTracker over Sentry: self-hosted, in the same database, and its only dependencies were already ours; on its own it sees requests, LiveViews and Oban jobs, so the logger handler adds GenServer, proc_lib and Task crashes. Thresholds sit above normal jitter (a live channel without a reading for 5 minutes has missed five polls). ErrorTracker stores request params and LiveView event params as they came, so a crash in the login or an invitation stored the password and TOTP code; a filter on the stored context is the mechanism ErrorTracker offers, and it catches every source (plug, LiveView, Oban, our logger handler) in one place.

## Removal Requests

**Current:** A channel has a `public` flag: hidden, it disappears from every public page, list, leaderboard and data endpoint, and its data stays. "Delete all data" (the slug typed again) queues `Workers.DeleteChannel` on the collector, which stops tracking, deletes every row of the channel including its webhook events, then the channel, and resyncs subscriptions; the channel's Kick id goes into `removals` (as a privacy deletion's user id does), so an import can't bring it back, until an admin adds the channel again by hand. Every request to Kick carries a User-Agent naming the site and a contact (`KICK_USER_AGENT`, or built from `SITE_NAME`, `PHX_HOST`, `CONTACT_EMAIL`). (updated 2026-09-24 07:15)

Hiding first answers a streamer at once without losing anything if the request is withdrawn; deletion is the explicit second step. Deleting raw facts is, with privacy deletion, the only exception to append-only, and both are audited.

## Renames

**Current:** The 5-minute `/channels` poll reports each channel's slug by broadcaster id, and that is the truth for that channel. When it reports a slug another active channel still holds here (renamed or banned and missing from the answer, or two renames within one poll), the other channel is the stale holder: its slug becomes a placeholder `<old slug>~<id>` (no real slug can contain `~`), its slug period is closed, and an error is logged for the admin; it gets its real slug when Kick reports it. Deleting a channel stops its processes and writes out the journal before deleting; a journaled write for a channel that no longer exists is dropped by the Writer (what it holds for other channels is written), not set aside. (updated 2026-09-24 21:45)

The unique index on active slugs made such a rename raise in the Writer, so the write was set aside forever and the renamed channel kept its old slug (and v2, read by slug, failed for it). Keeping the old holder's slug would have left the channel Kick names wrong; a placeholder keeps both rows valid and makes the stale one visible. Writes for a deleted channel can't apply anywhere; setting them aside would only raise an alert for nothing.

## Export and Import

**Current:** From `/admin/transfer` only (no command line). An export is a `.zip` written with Postgres `COPY`: `manifest.json` plus one CSV per table with a header row, keeping local ids so the files join for analysis as they are. Scope is the channel list alone (channels, slugs, groups, removals) or with history for an optional UTC date range; raw facts and admin corrections only (derived tables and admin accounts, audit log, settings stay). An import is uploaded, previewed from its manifest, then confirmed; the collector loads every CSV into a staging table (`LIKE <table> INCLUDING DEFAULTS`) and inserts through id maps built on natural keys, `ON CONFLICT DO NOTHING`, in one transaction, then queues a rollup rebuild over the imported range. A `removals` table (kind, Kick id) is written by privacy and channel deletions and travels with every export, so a removal on either side stays in force: removed channels aren't created, channels the other side removed are deleted here after the import, and removed users' rows are removed again with `Privacy.delete/1`. Files live in `TRANSFER_DIR` (a volume both roles mount) for 7 days. (updated 2026-09-24 17:00)

The owner wants to move and merge data between instances, share the channel list, and analyse data elsewhere, all from the admin UI. CSV serves all three: the same file re-imports and opens in a spreadsheet or pandas; `pg_dump` was ruled out because it can't merge into a database with its own ids and history. Merging on natural keys with existing rows winning keeps imports append-only and idempotent (AGENTS.md §7); overwriting on conflict would let a file silently change recorded history. `COPY` in and out keeps millions of rows fast and out of the BEAM's memory, and `:zip` streams large files (measured at ~80 MB resident for a 540 MB file). Mapping in SQL through staging tables rather than row by row in Elixir keeps a large import to a few statements. Imported open coverage periods are closed at the export's time, since the other collector stopped vouching for them then; per-user chat rows older than the 90-day retention are skipped. Known limit: if two collectors sessionized the same broadcast with different `started_at`, both streams are kept; merge them with a correction. Adding a channel by hand lifts its removal, since the admin chose to track it again.

## Security

**Current:** A Content-Security-Policy on every page with a per-request nonce for the one inline script (and for LiveDashboard and ErrorTracker), styles allowed inline (Tailwind, chart styles); rate limits with PlugAttack keyed on the visitor's address, read from `X-Forwarded-For` only when the request comes from a private address and only `TRUSTED_PROXY_HOPS` entries from the right; the admin behind Caddy's `ADMIN_ALLOW` networks plus password and TOTP. Failed admin logins are counted by our own entries in PlugAttack's ETS table, one per failure (20 in 10 minutes bans the address for an hour), not by PlugAttack's `fail2ban`. (updated 2026-09-24 20:00)

A browser check with the CSP on found no violations: charts (dynamic import), the LiveView socket and both dashboards work. Reading the leftmost `X-Forwarded-For` entry would let anyone choose their address and dodge limits; the rightmost-N rule trusts only what our own proxies appended. Login throttling plus a ban after repeated failures sits on top of TOTP, which already makes guessing hopeless, to keep the password hashing cost from being an easy load. `fail2ban` keys its sliding-window entries by the millisecond, so failures landing in the same millisecond overwrite each other: 20 failures fired at once counted as one, and a parallel burst was barely counted (it also made the ban's test fail about four times in five). A unique key per failure counts every one; the storage's cleaner expires them like its own rows.

## Data Quality

**Current:** `Metrics.Outliers` flags a reading that is 0 between two readings of 20 or more, or more than twice (and 50 above) both steady neighbours, only when both neighbours are within 150s; flags are derived (`viewer_flags`, recomputed with the rollups) and only change peaks. `Events.Shape` checks each stored webhook's type, version and the fields its handler reads; problems are counted per kind in `payload_issues` and alerted. The clock alert compares Kick's send time with our receive time (median over an hour, more than 30s). (updated 2026-09-24 07:45)

A glitch can't be told from a real event with one reading of context in general; these rules only catch the two shapes the design names and err towards not flagging (a raid that stays, a stream ending, a tiny channel's zero are all left alone, and tested). Excluding flags from averages was rejected: one reading barely moves an average, and dropping data from it would be an edit in disguise. Recorded webhooks all pass the shape check (a test), so a failure means Kick changed something.

## Recorder

**Current:** Recorder as mix tasks in `sim/` (the future simulator's project), one per source, writing raw recordings to git-ignored `sim/recordings/` with secrets redacted at write time; `mix fixtures.anonymize` is the only path into `fixtures/`. Anonymization is rule-based by field name and context with a persisted real→fake mapping (every number under an `*_id` key is mapped except a small safe list; UUIDs, whole or embedded in longer strings (media file names), and opaque string ids get consistent same-shaped fakes; strings directly in a list get the list key's rules; JSON nested in strings is anonymized inside; our app's webhook subscription and message ids are kept because they must match the webhook headers), reports unmatched text fields by path for human review, and is followed by an independent leak check that searches the output for every real name, text and id from the raw files and fails the run if any is found. Pusher via Mint.WebSocket; webhook capture via Bandit + a response policy that can fail on purpose to observe Kick's retries. (updated 2026-09-24 21:30)

A generic "anonymize every string" approach was rejected: it would destroy event names, categories and languages the simulator needs. Rules + a report of what fell through keeps useful data and makes leaks visible. The leak check exists because the rules alone missed a real case on the first real data (`chatroom.chatable_id`, the channel id under an unexpected name); its criteria are deliberately simpler than the rules so a gap in them shows up. UUIDs were first kept as-is (to keep reply links); they're now mapped consistently instead, since a VOD's UUID points straight at the real channel's video and consistent mapping keeps the links anyway. A UUID embedded in a media file name (`<uuid>___fullsize_….webp`) once slipped through because strings directly inside lists skipped the rules; both gaps are closed, and a test over the committed fixtures (no raw data needed) rejects any UUID that isn't a fake. Real signed webhook bodies stay only in `sim/recordings/` (anonymized bodies can't carry a valid Kick signature); the simulator signs with its own key. `websock_adapter` added as a test-only dependency for a local fake Pusher server; it will likely become a regular dependency when the simulator serves Pusher in phase 1.

## Simulator Design

**Current:** Everything the fake Kick answers is a pure function of simulated time and the channel's seed (`Schedule`, `Curve`, `StreamState`, `Payloads`); processes only serve HTTP and deliver webhooks. One port serves all three Kick hosts. Payload shapes are checked against `fixtures/` in a test. (updated 2026-09-24 07:00)

Time-addressable state means the simulator can restart, be asked about the past, or run fast with no stored history, and it makes bulk history a writer over the same functions rather than a second simulation. One port keeps scenarios simple (three env vars, one base URL) and matches how the probe's end-to-end test already worked. The shape test against fixtures is what keeps "built from the fixtures" true over time rather than a one-off.

Bulk mode moved from phase 1 to phase 2: it writes the raw fact tables, which don't exist until the schema does.

## Simulated Event Rates and Shapes

**Current:** The simulator produces all ten documented event types. Rates scale with the audience and are tuned so a three-hour stream with a few thousand viewers gives hundreds of follows, tens of subs, a handful of mostly-small gift bursts, and a few bans and redemptions. Shapes for the seven event types not yet recorded follow Kick's documentation and are marked as such in `Sim.Payloads`. (updated 2026-09-24 08:00)

The first rates were far too high (a 9 000-viewer stream produced 3 400 follows and 1 000 gifted subs in three hours), which would have made any metric built against the simulator meaningless. Doc-based shapes are a deliberate exception to "don't write fixtures from the docs": they are simulator code, not fixtures, and the open question in §16 tracks re-checking them. `Sim.Webhooks.event_types/0` is the single list, used by both the simulator and `mix record.subscribe`, so a new event type is added in one place.

## Simulator Pusher and Delivery

**Current:** The fake Pusher runs on the simulator's port, speaks protocol 7 as Kick's chat uses it, and copies real Pusher's refusals (4001 wrong key, 4201 missed pong, 4200 via a fault). Webhook deliveries run concurrently, one task per attempt. Recorder writes use a VM-wide unique sequence number and an atomic rename. `websock_adapter` is a regular dependency now. (updated 2026-09-24 09:00)

Concurrent delivery matches Kick and matters: delivered one at a time, thousands of `chat.message.sent` webhooks held up a stream-end event. Making delivery concurrent then exposed a real recorder bug: sequence numbers taken from the folder's file count collided under concurrent writes, keeping only 20 of 200 files in a test; the real Kick delivers concurrently too, so a busy channel's recording could have lost webhooks. The low-rate recordings made so far show no sign of loss. Pusher `created_at` stays `+00:00` (not `Z`) because that's what the recording shows.

## Simulator Control

**Current:** Manual control (control API at `/_sim`, `mix sim.ctl`) works through overrides stored with each channel (streams started by hand, streams cut short, title/category changes), layered over the schedule in `Schedule` and `StreamState`. Scenario changes are pure functions in `Sim.Control`. Channel processes re-read their channel each tick. Control answers report events as `emitted`, not `delivered`. (updated 2026-09-24 10:00)

Flags set on processes would have broken the rule that the simulation is a function of time (restarts, history, fast clocks). Overrides keep it: a manual stream is just another window. A stream cut after it was first seen still reports its real end, because the end event resolves the window's current version. The first version said `delivered` for events that, with no webhook URL, went nowhere; a real run showed it, so the field was renamed. The control API has no auth: the simulator binds loopback only.

Phoenix's generated `app/AGENTS.md` is kept, subordinate to the root one. (updated 2026-09-24 10:30)

TimescaleDB's compression SQL was checked on the running version before the migration (2.30 uses the `columnstore` names). Hypertable foreign keys to `channels` and `streams` are kept: correctness over the small insert cost. `categories` isn't created yet; `viewer_samples.category_id` is Kick's id without a foreign key until it is.

## Receiver

**Current:** `ingress/receiver` is its own Elixir app (Bandit, Plug, `amqp`, SQLite via `exqlite`). It verifies, builds the envelope, publishes with confirms and `mandatory`, spools to SQLite (WAL, `synchronous=FULL`) on any failure, and answers 200 only when the delivery is confirmed or on disk (503 otherwise, including any unexpected error). Returns are registered with `:amqp_channel` directly. Every wait is bounded: confirms (`CONFIRM_TIMEOUT_MS`, passed as milliseconds), a delivery's call to the publisher (that plus 1s, then spool), Kick's key (read from `:persistent_term`, refetched in a task, a failed signature waits at most 3s). One reconnect path with backoff and jitter. `/health` reads state from memory and says 503 after `HEALTH_BROKER_GRACE_S` without RabbitMQ only if the peer receiver (`PEER_HEALTH_URL`) can publish. Headers are checked against the envelope schema (400), and deliveries signed more than `MAX_EVENT_AGE_S` (3 days) ago are refused (400). RabbitMQ topology and least-privilege users come from `deploy/rabbitmq/definitions.dev.json`, with a `test` vhost mirroring development. (updated 2026-09-24 22:00)

Publishes go one at a time, which caps throughput around the broker's confirm latency; ample for webhook volumes (hundreds a minute at 1 000 channels) and it makes "the return in the mailbox belongs to this publish" true. The `amqp` library's return relay broke the return-before-ack ordering, so an unroutable message looked confirmed: found by a test, fixed by registering directly (verified 200/200). A closed channel made `wait_for_confirms` exit and crash the publisher; now caught, and a test asserts the same process survives. The spool deduplicates by message id, so Kick's retries don't pile up. Loading definitions removed RabbitMQ's default `guest` user, which is fine (one account fewer); the app now uses its own consume-only user.

An audit found: each `:DOWN` (connection and channel) started its own reconnect loop and never closed the old connection (1 → 6 connections after three kills); `wait_for_confirms(chan, 5000)` meant 5000 *seconds*, so a silent broker held the single publisher for the client's ~60s call timeout while the router waited forever and `/health`'s call queued behind it (Caddy's 2s check then marked both receivers down); a bad signature ran the key fetch inside the key server, timing out every concurrent delivery. The health rule needs the peer because "503 whenever RabbitMQ is gone" would, with the broker itself down, take both receivers out and turn a recoverable outage into lost webhooks; a receiver that lost the broker while its peer has it should step aside, so the peer's check is polled in the background and the step-aside is conditional. The spool gets a warning size, not a cap: refusing deliveries loses data, a full disk is an alert. The event age limit is lenient because Kick retries for about a day and an old *unseen* delivery is still real data; it only stops much later replays of captured deliveries (the app already ignores repeats by message id). Unparseable `sent_at` is passed on for the app to dead-letter rather than refused, so a Kick format change can't make the receiver drop everything. `event_type` stays unsigned: the app trusts it as far as the ingress and queue, and the shape check flags a relabeled body; rejecting on a type/body mismatch was ruled out because a Kick payload change would then dead-letter every event of that type.

## Queue Consumer

**Current:** `Events.Consumer` is Broadway on `broadway_rabbitmq`. Undecodable or wrongly signed messages are rejected to the dead-letter queue explicitly; everything else requeues. A batch is stored in one transaction; if the database can't take writes for a while (a connection error, or a Postgres error of SQLSTATE class 08, 53, 57 or 58, or 40001, 40P01, 25006, 55P03) the batch waits and retries with backoff (messages stay unacknowledged); if one message breaks the transaction for another reason, the batch is stored one message at a time so only that one is dead-lettered. A missing Kick public key is waited out, not held against messages; a failed signature is retried only with a different, freshly fetched key, and a fetch that doesn't finish within 15s requeues the message. The key is read from `:persistent_term` and fetched in a task. `ProcessEvents` pages through all unprocessed events with a cursor, leaving out channels it skipped; `unprocessed_for/1` filters on the stored `broadcaster_user_id` in SQL (rows from before that column are checked by body). (updated 2026-09-24 22:00)

The quorum queue dead-letters after 10 deliveries, so plain requeue-on-failure would dead-letter every good event during a short database outage: waiting inside the batcher keeps them in RabbitMQ instead. An audit found that only lost connections counted as an outage, so a shutdown, failover to a read-only node, full disk or statement timeout dead-lettered good events; classifying by SQLSTATE class keeps "the database can't now" apart from "this message can't ever" (constraint, data and syntax classes still dead-letter). A statement timeout is waited out like the rest: a batch of inserts that always times out would be a database problem to fix, not something to push into the dead-letter queue. Facts that need no channel state are written in the same transaction; stream status and metadata are handed to the channel's process after the commit and stay unprocessed in `webhook_events` until it handles them (on start it catches up; `ProcessEvents` retries every 5 minutes, marking events of untracked channels processed). It used to read only the 500 oldest, so 500 events of one stopped channel starved every other channel; paging fixes that without marking the stopped channel's events, which it must still handle when it starts.

## Metadata Changes

**Current:** The pure `Metrics.Changes` builds `stream_changes` for title, category, language and mature flag. A metadata event's snapshot is compared with the previous one; a snapshot older than the latest applied is ignored. The poll fills in missed changes but only counts a difference seen twice in a row, never within 120s of an event, dated at the first sighting. A stream's first values are recorded with no old value. A snapshot arriving while no stream is open is held (in memory and the journal snapshot) and applied to the next stream only if it came at most 5 minutes before that stream's start; an older one is dropped. A stream closed from polling that reopens continues its change log (from memory, or from `stream_changes` after a restart). (updated 2026-09-24 21:45)

The API lags Kick: right after a metadata event, the poll can still show the old title, and a naive comparison would record the title changing back and forth. Two sightings plus a quiet period after events removes that without losing changes whose events were missed (they are dated up to a minute late).

A held snapshot used to wait forever: a metadata event from days before became the first values of whichever stream opened next, labelled `event`, and the poll then recorded a change back, in a log that is append-only. A status event and its stream's first metadata event come within seconds of each other; 5 minutes leaves room for delivery delays and replays while excluding anything that described an earlier stream. The event is marked processed once held; if the process restarts outside its lease term before the stream opens it is lost, and the stream's first values come from the next poll instead (dated up to a minute late), which was preferred to keeping events unprocessed on an in-memory condition. A reopened stream used to start an empty log, so its next poll recorded a "first value" without the two-sightings rule and with no old value.

## Coverage

**Current:** `coverage` periods are always closed: each outcome extends the latest period for that channel and source if the result is the same and the previous outcome is recent (a little over the source's cadence), otherwise starts a new one; `to_at` is nullable in the schema but always written, and a null would cover nothing. Sources: `api` (60s poll), `subscribers` (5-minute `/channels` poll), `chat`, `followers`, `ingress`. A period says what was written, per channel: `api` is recorded by each `ChannelServer` for the reading it handled (a reading no process was there to handle is a gap), `subscribers` only for channels whose totals were in the answer, and an answer whose meaning couldn't be recorded (the source's code raised) is no coverage. A failed request is recorded failed for every channel it was for. `ingress` is recorded by `SubscriptionSync` every 15 minutes: ok for a channel whose webhook subscriptions are all in place at Kick, failed for one whose subscribing failed, nothing when Kick's list couldn't be read. Webhook counts (follows, subs, gifts, Kicks) are 0 only where it says we were receiving. (updated 2026-09-24 21:50)

An open period (`to_at` null) would keep claiming coverage after a collector dies; closed periods make any time no period covers unknown, i.e. a gap, which is the invariant. Failed outcomes are stored too, so the site can tell "Kick didn't answer" from "we weren't running". Recording a whole batch as covered when the request succeeded counted readings dropped because a channel's process was down, and channels Kick left out of its answer, as collected. The subscription check stands for webhook reception because nothing else knows per channel whether events can arrive: Kick retries a delivery for about a day, so a receiver or consumer outage shorter than that loses nothing, while a missing subscription loses everything. History from before `ingress` was recorded has no coverage, so its webhook counts read as unknown after a rebuild, which is the truth.

## Webhook Subscriptions

**Current:** `SubscriptionSync` (Oban, on every change to the tracked set and every 15 minutes) subscribes each active channel to the seven event types we use (status, metadata, follows, subs, resubs, gifts, Kicks), removes subscriptions of untracked channels, duplicates and unused types, and restores ones Kick cancelled. The delivery URL is set once in the Kick app's settings. (updated 2026-09-24 12:40)

A sync also runs when the collector boots, so a fresh collector gets its webhooks at once (found in the live run: it waited for the next cron). Kick's subscription API takes a broadcaster, event types and `method: webhook`, with no URL, so "pointing at the ingress URL" in the plan is an app setting, not code. Bans, redemptions and chat aren't subscribed: nothing reads them (chat comes from Pusher).

## Jobs

**Current:** Oban runs on every node; its queues (`kick`, `followers`, `alerts`, `transfers`) start paused and run only on the leading collector, which resumes them when it takes the lease and pauses them when it gives it up (checked every tick, locally). A web node and a standby only insert jobs. Cron (inserted by whichever node Oban elects): `SubscriptionSync` every 15 minutes, `ProcessEvents` every 5, `Alerts` every minute (its own queue, so long jobs can't delay it), rollups. Every worker has a time limit. (updated 2026-09-24 18:00)

Admin actions on the web node need to enqueue work the collector runs; one Oban config with leadership deciding where queues run keeps that simple, and keeps jobs that write collected data where collection runs. Pausing and resuming go through Oban's notifier, so each tick re-checks the queues' local state and repeats what a database blip may have dropped.

## Facts from Events

**Current:** Follows, subs, resubs, gifted subs and Kicks are parsed by the pure `Events.Facts` and written in the same transaction that stores the event, only for tracked channels. They carry no stream id; stream attribution is by time at read time. Usernames go only to `kick_users` (a later sighting's name wins). Kicks messages are never read. (updated 2026-09-24 13:10)

That makes the result depend on arrival order: a follow stored before its stream's start event would be attributed to no stream forever (raw facts are never updated). ## Follower Readings

**Current:** A polled source (`Collector.Sources.Followers`) reads v2: every 15 minutes while live, daily while offline, one channel per request, one at a time, three per 15-second cycle. A failed reading is a gap; a channel whose readings keep failing backs off: retried 10 minutes after the first failure, doubling up to 6 hours, reset by a success, with the failures kept in the journal across restarts. Requests (a stream's start and end, a channel added) are served within a second whatever the backoff; from a web node they travel as a `FollowerPoll` job, which runs on the leader and hands the request over. When each channel was last read is loaded from the database once, and kept in memory after. (updated 2026-09-24 21:45)

Replaced the Oban `FollowerPoll`-per-reading plus `FollowerSchedule` pair: as a source it gets the runner's cadence, isolation, coverage and journaled writes like the other sources, and no longer needs the database to decide or to write. The per-cycle limit replaces the random delays that kept v2 from seeing bursts. A fixed 10-minute retry meant a channel v2 no longer answers for (Cloudflare blocking the server, a 404 after a rename) was tried 144 times a day instead of once; the backoff brings that to 9 on the first day and 4 a day after, still noticing within hours when v2 answers again. 6 hours, not a day, so a live channel's gain isn't lost for long; start and end requests still go through.

## Rollups

**Current:** `stream_stats` and `hourly_stats` are caches recomputed by an Oban job (last 3 hours every 5 minutes, last 48 hours nightly), by a replay of stored webhooks (it queues the `rollups` job of its range, a minute after it finishes) and by `mix kick_tracker.rebuild` (from the earliest raw fact of any kind by default), not TimescaleDB continuous aggregates. Rebuilds of `hourly_stats` run inside a transaction-scoped advisory lock and upsert their rows. Hours watched: each sample weighs the time since the previous sample of its stream (the first, since the stream's start), capped at 75s, in every figure (a merged stream's parts each from their own start; category figures from one cap before the range, like the hourly rollup); `KickTracker.Metrics` is the reference and the SQL rollup is property-tested to agree with it. Stream figures count follows, support and chat by time between start and end. Follower gain uses the readings closest to the start and end, within 30 minutes, else null. (updated 2026-09-24 21:50)

Continuous aggregates can't use window functions, and Σ viewers × min(Δt, 75s) needs each sample's neighbour; Toolkit's time-weighted averages aren't in the community image. Approximating hourly hours watched as Σ viewers × 60s would make hourly and per-stream figures disagree. A backward weight puts each sample's contribution in the hour it was taken, so hourly figures add up exactly to the stream's. Recompute-by-range caches are also cheap to change when a formula changes, which continuous aggregates are not. The 5-minute job, the nightly one and an admin's reprocessing run on a queue of five, so overlapping rebuilds happened and the second's plain INSERT hit the first's rows; one lock serialises them (a rebuild of three hours takes well under a second) and the upsert keeps any path that skips the lock idempotent. Chaining the rollups after a replay, rather than queueing both at once, makes sure they see what the replay wrote.

## Bulk Mode

**Current:** `KickTracker.Bulk` and `mix kick_tracker.bulk` live in `app/dev/`, compiled only in dev and test, and write a scenario's history straight into the raw tables from the simulator's pure functions: streams closed by an end event, a sample every 60s at a per-stream offset, change logs from `StreamState` segments, facts from `Events.for_minute` (message ids `bulk:…`), chat bucketed by clock minute, followers (15 min live, at start and end, noon on other days), subscribers every 5 minutes, one coverage period per source; then the rollups. Only streams that ended before `to`. Idempotent (inserts ignore existing rows). (updated 2026-09-24 14:40)

A path dependency on `../sim` limited to dev/test, plus a dev-only source directory, keeps the simulator out of production builds entirely. Writing rows directly instead of replaying webhooks through the pipeline makes months of history take minutes; the pipeline itself is covered by the integration tests. Bulk facts have no `webhook_events` rows, so they can't be rebuilt from events: acceptable for development data only.

## Unknown Is Null

**Current:** Derived figures with no underlying data are null, not zero: `avg_viewers`, `peak_viewers` and `hours_watched` in `stream_stats` and `hourly_stats` when there are no viewer samples; follower totals and gain without a reading near the start or end; a stream's follows, subs, resubs, gifted subs and Kicks unless `ingress` coverage covers at least 99% of it (columns made nullable, expand only); a period's webhook sums when no ingress coverage touches it at all, and otherwise they come with `ingress_coverage` (the covered share) so a partial sum can be marked; support chart buckets where the ingress wasn't covered. (updated 2026-09-24 21:50)

A zero would read as "nobody watched" when it means "nothing was measured", the same mistake "gaps are gaps" forbids for raw data. Readers use `samples` and `coverage` to tell an offline hour from an unmeasured one. 99% rather than 100% for a stream: coverage periods are extended by 15-minute checks padded by a cadence, so a covered stream can still show a few seconds of rounding at its edges; a stretch that matters is well over 1%. Hourly rows keep 0 for their webhook counts (a row exists whenever anything happened in the hour); the period readers apply coverage instead.

## Configuration

**Current:** Every setting comes from the environment, and a variable set to nothing counts as not set: `config/runtime.exs` (app and receiver) removes empty variables before reading any. (updated 2026-09-24 22:05)

The env file examples keep optional settings as empty lines (`HEARTBEAT_URL=`) so they're easy to fill in later, and Docker passes them as empty strings. Read as values, an empty heartbeat or alert URL was called and failed ("scheme is required"), an empty shadow database URL was connected to and failed (no database), and an empty number (`BACKFILL_DAYS=`) failed to parse at boot. Treating empty as unset everywhere, once, was preferred over checking for `""` at each setting, which the next setting added would forget. The one setting that gave empty a meaning of its own (`COLLECTOR_STATUS_PORT=`, off) lost it; nothing used it, and the container healthcheck already read empty as the default port.
